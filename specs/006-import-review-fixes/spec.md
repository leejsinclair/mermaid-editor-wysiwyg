# Feature Specification: Import Review Fixes

**Feature Branch**: `feature/006-import-review-fixes` (from `main`; feature 005's PR #4 was merged before these fixes)

**Created**: 2026-10-21

**Status**: Draft

**Grilled on**: 2026-10-21

**Input**: User description: "Bug fixes from reviewing the pull request for feature 005 (New from Mermaid). Nine inline review comments, all confirmed against the code: C4 text is not decoded on import; selecting a report line keeps re-selecting it; clearing the text leaves the old diagram importable; compare can use huge amounts of memory; a multi-line `%%{init: … }%%` directive is misread; a second diagram header still reaches the parser; the report does not say what an approximated item became; an unreadable file fails with no message; the 100-node performance test cannot fail. Fix all nine, each test-first."

This feature corrects behaviour that feature 005 (`specs/005-new-from-mermaid/spec.md`) already requires. It adds no new capability. Where this spec refers to an FR, EC or SC of feature 005 it is written "005 FR-nnn".

## Clarifications

### Session 2026-10-21

- Q: Import can use an outdated preview after any edit, not only after clearing the text; how wide should the fix be? → A: Disable Import whenever the text differs from the text the preview was read from, including empty text.
- Q: What does the compare view do with very large texts? → A: Use an exact comparison whose memory grows with the text size; only past a work limit fall back to a simpler comparison (unchanged lines matched at the start and end, the middle marked as changed), with a note in the view.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - C4 text survives a round trip (Priority: P1)

A developer exports a C4 diagram whose labels, descriptions or technologies contain special characters (for example `R&D`, quotes, `<`, `#`), then starts a new diagram from that exported text. The imported diagram shows exactly the text the developer originally typed, and exporting it again gives the same source.

**Why this priority**: Today the editor corrupts its own C4 output on import, and every further export makes it worse (`R&D` → `R#38;D` → `R#35;38#59;D`). This is silent data corruption of user content, which the constitution forbids (Principle IV) and 005 FR-009 already rules out.

**Independent Test**: Create a C4 diagram with special characters in every text field, copy its generated source, import it, and compare field values and regenerated source.

**Acceptance Scenarios**:

1. **Given** C4 source generated by the editor for an element labelled `R&D` with description `"fast" <cheap>` and technology `C#`, **When** it is imported, **Then** the element's label, description and technology read `R&D`, `"fast" <cheap>` and `C#`.
2. **Given** that imported diagram, **When** its source is generated, **Then** it equals the source that was imported.
3. **Given** C4 source with escapes in a boundary label, a relationship label, a relationship technology and the diagram title, **When** it is imported, **Then** each is decoded the same way flowchart and sequence labels are.

---

### User Story 2 - The dialog never imports stale or wrong content (Priority: P1)

A developer clears the paste area, or edits text after selecting a report entry. The dialog only ever offers to import what is currently in the paste area, and typing behaves normally.

**Why this priority**: Two defects cause the dialog to act on something other than what the developer sees or typed: after clearing, Import briefly creates the previous diagram; after selecting a report entry, each keystroke replaces the whole highlighted line. Both produce a wrong result from an ordinary action.

**Independent Test**: In the dialog, paste a valid diagram, clear the text and click Import at once; separately, select a report entry, click into the text and type several characters.

**Acceptance Scenarios**:

1. **Given** a valid diagram in the paste area with its preview shown, **When** the developer empties the paste area, **Then** at once (before any preview delay) Import is unavailable and the previous preview is no longer shown as importable.
2. **Given** the paste area was just emptied, **When** the developer activates Import by pointer or keyboard within the preview delay, **Then** no diagram is created.
3. **Given** valid text A with its preview shown, **When** the developer changes it to valid text B, **Then** Import is unavailable until B's preview is ready, and activating it then creates diagram B, never A.
4. **Given** the developer selected a report entry and its line is highlighted, **When** they place the caret and type several characters, **Then** each character is inserted at the caret and no text is replaced or reselected.
5. **Given** the developer typed after selecting a report entry, **When** they select the same or another entry again, **Then** that entry's line is highlighted once.

---

### User Story 3 - Directives and extra diagrams are handled as reported (Priority: P2)

A developer pastes a document that begins with a `%%{init: … }%%` directive spread over several lines, or a document holding a second diagram header after the first diagram. The editor detects the diagram type correctly, imports the first diagram, and the report's statements match what actually happened.

**Why this priority**: Real READMEs commonly use multi-line init directives; today such a supported diagram is refused as unsupported. A second header is reported as ignored yet still reaches the parser and can make the import fail, so the report is not honest (Principle V, 005 EC-01, EC-02).

**Independent Test**: Import a flowchart preceded by a three-line init directive, and a document with two `flowchart` headers; check the detected type, the import result and the report entries.

**Acceptance Scenarios**:

1. **Given** a flowchart whose `%%{init: … }%%` directive spans several lines, **When** it is pasted, **Then** the diagram is detected as a flowchart, imports, and the report lists the directive once as ignored with its starting line number.
2. **Given** a sequence or C4 document with a multi-line init directive, **When** it is pasted, **Then** its type is detected correctly.
3. **Given** a document with a complete first flowchart followed by a second `flowchart` header and more nodes, **When** it is imported, **Then** only the first diagram's content is parsed and imported, the import does not fail because of the second diagram, and the report lists the second diagram as not imported with its line number.
4. **Given** a directive that opens with `%%{` but is never closed, **When** it is pasted, **Then** the dialog reports the problem with its line number rather than guessing a diagram type from text inside the directive.

---

### User Story 4 - Clear feedback for approximations and unreadable files (Priority: P2)

A developer reads the Import report and sees, for every approximated item, what it became. A developer who chooses or drops a file that cannot be read sees a message in the dialog saying so.

**Why this priority**: 005 FR-006 requires approximated entries to say what the item became (the contract's example is "Kept as a rectangle."), and Principle V requires failures to give understandable feedback. Today the first is missing and the second fails silently.

**Independent Test**: Import a flowchart with an asymmetric node and read its report entry; choose a file whose read fails and observe the dialog.

**Acceptance Scenarios**:

1. **Given** a flowchart with an asymmetric-shape node on line 7, **When** it is previewed, **Then** the report entry for line 7 names the asymmetric shape and its reason, and ends with "Kept as a rectangle."
2. **Given** any approximated construct, **When** it appears in the report, **Then** its entry names what it became, and the accessible text of the entry includes that as well.
3. **Given** a chosen or dropped file whose contents cannot be read (removed, permission denied, read error), **When** the dialog tries to load it, **Then** the dialog shows an understandable message that the file could not be read, the paste area and preview are unchanged, and no error escapes unhandled.

---

### User Story 5 - Compare stays responsive for large texts (Priority: P3)

A developer opens the compare view for a large document (up to the editor's 5 MB file limit). The view opens without freezing or crashing the tab.

**Why this priority**: The current comparison's memory grows with the product of the two texts' line counts; two 10,000-line texts need about 100 million cells. It is rare but can lose the developer's session.

**Independent Test**: Open the compare view for two texts of 10,000 lines each and measure time and memory.

**Acceptance Scenarios**:

1. **Given** an original and a generated text of 10,000 lines each, **When** the compare view is opened, **Then** it is shown within 2 seconds and the tab stays responsive.
2. **Given** texts so large or so different that the exact comparison would pass its work limit, **When** the compare view is opened, **Then** it shows both texts side by side, marks unchanged lines at the start and end as same and the middle as changed, and states plainly that the marking was simplified for size.
3. **Given** texts within the work limit, of any length up to the file limit, **When** compared, **Then** the result marks a minimal set of removed and added lines, as the current comparison does, and no simplification note is shown.

---

### User Story 6 - The 100-node performance check proves the budget (Priority: P3)

The automated check for 005 SC-005 (preview within 1 second for 100 nodes) fails if the new 100-node preview is not shown within 1 second.

**Why this priority**: The check currently passes on the earlier warm-up picture, so the recorded evidence for SC-005 (verification VO-050) does not show the budget is met. It must be able to fail before its pass means anything.

**Independent Test**: Run the check against a build where the preview is artificially delayed beyond 1 second; it must fail. Run it against the normal build; it must pass and the measured time is recorded.

**Acceptance Scenarios**:

1. **Given** the warm-up picture is shown, **When** the 100-node text is pasted, **Then** the check waits for content that exists only in the new picture (for example the label "Node 100") and measures time to that.
2. **Given** the preview takes longer than 1 second, **When** the check runs, **Then** it fails.
3. **Given** the normal build, **When** the check runs, **Then** it passes, and the measured time is recorded as the evidence for 005 SC-005 in place of feature 005's earlier run.

---

### Edge Cases

- EC-01: An emptied paste area followed at once by new text: Import stays unavailable until the new text's preview is ready, and then imports the new text only.
- EC-02: Text that is only whitespace counts as empty for EC-01 and User Story 2.
- EC-03: A C4 field containing a literal `#` followed by text that looks like an escape (typed by the developer as `#38;`) generates and re-imports as typed (the editor's own escaping makes this unambiguous); text from other tools follows the same decoding as flowchart labels, including the known limit in 005 EC-03.
- EC-04: An init directive that opens and closes on one line keeps working as today.
- EC-05: A second diagram header inside a Markdown block's first diagram is handled as in User Story 3; further Markdown blocks remain *ignored* per 005 FR-012.
- EC-06: A file read that fails after a successful earlier load leaves the earlier text in place.
- EC-07: Selecting a report entry while the text has changed since the report was made highlights the line by its current number, or does nothing if that line no longer exists; it never throws.
- EC-08: A line inside a directive that starts with a diagram word (for example an unquoted `flowchart:` key) is part of the directive and never a diagram header.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Importing C4 source MUST decode Mermaid escapes and entities in every text field the C4 import keeps (element and boundary labels, descriptions, technologies, relationship labels and technologies, and the diagram title), in the same way flowchart and sequence labels are decoded (005 FR-009).
- **FR-002**: For any C4 diagram the editor can build, importing its generated source and generating again MUST give the same source (no growth of escapes over repeated round trips).
- **FR-003**: Import MUST be available only when the preview was read from exactly the text now in the paste area and is ready and valid. Any change to the text MUST make Import unavailable at once, without waiting for the preview delay, until the new text's preview is ready. Emptying the text (or leaving only whitespace) MUST also remove the previous preview at once.
- **FR-004**: Activating Import MUST create a diagram from the text in the paste area at that moment, never from an earlier text.
- **FR-005**: Selecting a report entry MUST highlight its line once; later typing MUST insert at the caret and MUST NOT re-select the line.
- **FR-006**: A `%%{ … }%%` directive MUST be recognised whether it is on one line or spread over several; all of its lines MUST be skipped when detecting the diagram type, and it MUST be reported once as ignored with its starting line number (005 EC-01). An unclosed directive MUST be reported with its line number.
- **FR-007**: When a document contains a further diagram header after the first diagram, the further diagram's text MUST NOT be passed to the parser; only the first diagram is parsed and imported, and the report MUST list the further diagram as not imported with its line number (005 EC-02). A report statement that something was ignored MUST be true.
- **FR-008**: Every *approximated* Import report entry MUST show what the construct became, in the visible text and in the entry's accessible text (005 FR-006, contract `import-reading.md`).
- **FR-009**: A file read failure MUST be caught and shown in the dialog as an understandable message, MUST leave the paste area and preview unchanged, and MUST NOT produce an unhandled error.
- **FR-010**: The compare view MUST work for texts up to the editor's file size limit without freezing or crashing the tab: its memory MUST grow no faster than roughly the combined length of the two texts, and it MUST open within 2 seconds for two 10,000-line texts. It MUST use an exact comparison (a minimal set of removed and added lines, as now; existing compare tests keep passing) up to a work limit set in the plan; past that limit it MUST fall back to matching unchanged lines at the start and end and marking the middle as changed, and MUST say in the view that the marking was simplified.
- **FR-011**: The automated check for 005 SC-005 MUST measure time until content unique to the new diagram is shown, MUST fail when that takes more than 1 second, and its passing result MUST be recorded in this feature's evidence and replaces feature 005's VO-050 run as the evidence for 005 SC-005.
- **FR-012**: Each fix MUST be made test-first: a test that fails because of the defect is recorded before the fix (Constitution III), and no existing test may be weakened to obtain a pass.

### Key Entities

- **Import report entry**: one reported construct; has a kind (*dropped*, *approximated*, *ignored*), a source line number, a reason and, for *approximated*, what it became.
- **Directive**: a `%%{ … }%%` block before the diagram header, one or more lines long; not a diagram element.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For a set of at least 10 C4 diagrams covering each supported C4 kind and every escaped character the editor emits, 100% import with every text field equal to the original and regenerate to identical source, including after three successive round trips.
- **SC-002**: In 100% of attempts, activating Import within the preview delay after emptying or changing the text creates no diagram from the earlier text.
- **SC-003**: After selecting a report entry, typing 20 characters leaves all 20 in the text at the caret with no text lost.
- **SC-004**: 100% of sample documents with a multi-line init directive (flowchart, sequence and each C4 kind) are detected as the correct type.
- **SC-005**: 100% of documents with a second diagram header import the first diagram, and every report entry saying something was ignored is true.
- **SC-006**: 100% of approximated report entries name what the construct became.
- **SC-007**: 100% of simulated file read failures show a message in the dialog with no unhandled error.
- **SC-008**: The compare view opens for two 10,000-line texts in under 2 seconds without the tab becoming unresponsive.
- **SC-009**: The 100-node preview check fails against a deliberately slowed preview and passes against the normal build, with the measured time recorded.
- **SC-010**: All existing unit and end-to-end tests for features 002–005 still pass.

## Assumptions

- All nine review findings were confirmed against the code at commit `cdd33da`; no finding was a false alarm. Feature 005's PR #4 was merged before the fixes, so they go on their own branch and pull request.
- The required behaviour is already set by feature 005's spec and contracts; where they are silent (unclosed directives), this spec sets a reasonable default rather than raising a question.
- The compare view's work limit is a planning detail; it must be high enough that ordinary documents (a few thousand lines with modest differences) never reach it.
- "Within the preview delay" means the existing pause (about 300 ms) after the last change before the preview updates.
- The C4 decoding uses the same rules already used for flowchart and sequence labels, including the known limit recorded in 005 EC-03.
- No new runtime dependency is needed.
- Replying to each review thread, committing and pushing happen only when the user asks, after the fixes pass.
